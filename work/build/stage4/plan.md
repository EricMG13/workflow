## 0. Verification principle and threat model

Principle: for every recorded transition `before -> after`, the verifier re-runs the producer's own rule on `before` and requires `after` to be exactly what that rule yields. Where the rule depends on data the receipt cannot carry (uuid ticket ids), the verifier takes the recorded value and checks every invariant it must satisfy. Nothing is read from the attacker's bytes as truth; every lookup a forged record can reach is an explicit check (R4-4).

Attacker controls: every byte of the receipt; every file under the store directory (`blobs`, `snapshots`, `current`, `owner-run-audit/*` including `receipt.sha256`); the publication directory; and, equivalently, a patched runtime that writes those files (adv-4's `store.begin` patch). Out of scope: the verifier's code and its imports (owner cores, `deploy_vii`), the pack bytes other than by hash (a changed pack fails `store.pack`), core ticket authentication (QUEUE known gap 3), concurrent writes during a verify (`stale_binding`), and the analytical quality of genuine submissions.

## 1. Class A: replay `Execution.begin` (S1a HIGH 1, MEDIUM 1, LOW 1)

Producer rule (`src/deploy_vii/execution.py` `Execution.begin` :647-679): no pending attempt in the snapshot; `inputs = current_inputs(snapshot, module)`; `previous` = attempts of the same module and inputs; refuse if `previous and (len(previous) >= 2 or not previous[-1].issues)`; the new attempt is `Attempt(ticket_id, module_id, inputs, number=len(previous), repair_of=previous[-1].ticket_id or None, repair_issues=previous[-1].issues or ())`, status pending, no steps.

Today `_verify_begins` (:1518-1535) checks only ticket, module, number and "others unchanged"; `_verify_attempts` (:1928-1966) accepts any count of attempt 0; `_verify_publications` (:1692-1755) checks only that one deterministic attempt was added; `_verify_settlements` (:2088-2150) binds heads only, so attempts without a head (rejected attempt 0, failed CP-MODEL) are bound to nothing. That is the exemption HIGH 1 names; after this class no exemption remains because every attempt is bound at its own `before`.

## 2. Class B: `tamper`, `refusals`, `tool_use` sections, by mechanism

Every `cases/*-owner/expected.json` section maps onto one of three verifier mechanisms. No module-specific verifier code exists or is added.

B1 Result tamper (all `tamper` sections): a forged result Module with every hash re-cascaded passes `_verify_audit`, chain, submissions and settlements until `_PROBES[module]` rebuilds the head from the journaled payload and bound heads (`_verify_settlements` :2135). All 20 planned modules have a `_PROBES` row (:187-208). Gap: a module without a row raises `KeyError` at :2135 (fail-closed by crash, not a refusal). Change: `_check_specs` refuses an analytical spec without a `_PROBES` row at `create` (same shape as G1-X L2). RED: `tests/test_owner_stage4.py::test_analytical_spec_without_a_probe_is_refused_at_create`. Existing per-module tamper tests (cp1c :492, cp1d :309, cp2d :331 `STORE_RUNS`, cp2e :248, cp2g :478, cp2h :519, cp3 :409, cp3c :456 `STORE_RUNS`, cp3d :227/:252, cp4 :424, cp4c :493, cp8 :323, cpdr :210, cpl10 :345, s1a :909) stay as they are; the `STORE_RUNS`-gated and G2-skipped ones are deferred genuine runs, not Stage 4 code.

B2 Refusals: (i) a `refused` record reproduces exactly its gate issues and leaves the snapshot unchanged (`_verify_submissions` :2020-2040, `_gate`); (ii) an `invalid` step reproduces the entry validator's issues plus journaled rules (`_verify_invalid_step`, `_unbounded_step_issues`) and its repair chain holds (`_verify_attempts`); (iii) a refused tool call on a non-sourced step is `refused/not_permitted` with no body (`_verify_calls_reads` :1779-1785). With class A, "no attempt consumed" (every oracle's refused disposition) is now bound: a refused submission cannot be followed by a forged extra attempt. No further verifier change. Attack cases: drop one issue, reorder issues, change a refused record to invalid, forge an invalid step whose issues no validator yields (cf. `test_cp1a_invented_validator_issue_refuses`), forge a refused call as `ok` with a body.

B3 Tool use: sourced-step calls are replayed through `SourceSession.from_execution` (H1 scope, read evidence; :1771-1777); journaled rules are re-derived at the same evidence (`_journaled_issues`); the `read_inputs` body is recomputed (`_inputs`) and required before the fill (:1990-1995). The oracles' "exactly one read_inputs" is a genuine-driver statement; the runtime admits up to `MAX_CALLS` and the verifier binds each. Change: a static conformance test, `tests/test_owner_stage4.py::test_tool_use_sections_match_registrations`, parametrised over every `cases/*-owner/expected.json`: a "submit only" `tool_use` module has `sources=False` on every step; a module whose section names a host scope matches `host._SOURCE_STEPS`; a module whose section requires `read_inputs` has `inputs != "none"` and a `_VIEWS` row. It reads oracles as data and asserts against the registries only. Attack cases: an `ok` `read_pages` outside the H1 scope; `source_evidence` naming a page no call read; an altered `read_inputs` body; a sourced step with cited pages and zero reads forged `valid`.

Must not move: every oracle section and every per-module test. Nothing in this class may move under any current ruling.
