## Global Constraints

- **No stub or fake value standing in for real behaviour.** A step with no text raises a named `NoPrompt(step_id)`; the composer never falls back to a generic prompt. No placeholder scope, hash or period is inserted to satisfy `build` (see Task 2 on why `build` is not called for scope steps).
- **No catch-all that hides a failure.** Every `except` names the exception and re-raises or records a named fault. No fail-open is planned.
- **No network, no key, no environment read.** The composer is pure: it reads package files and the objects it is handed.
- **No `src/deploy_vii` change.** If a task finds it needs one, it stops and reports BLOCKED to the controller.

- **Python owns arithmetic.** Prompts say "never do arithmetic" as `build` does (`prompts.py:1181-1201`, rule 4).
- **Test command:** `PYTHONPATH=src "/Users/ericguei/Documents/Deploy Workflow/.venv/bin/python" -m pytest <paths> -q`; gates on changed files: `ruff check`, `ruff format --check`, `mypy`; full suite once before hand-off (ruling B3).

## Task 2: The composer, fences and `prompt_for` [security: mx-adversary]

**Files:** `prompts/fence.py`, `prompts/compose.py`; tests `tests/prompts/test_fence.py`, `test_compose.py`.

**Why not `build` for every step.** `build` (`prompts.py:1120`) refuses a step in `SCOPE_BLOCKS` without a `scope` (:1150-1151) and a step in `MODULE_CONTEXTS` (`live/context.py:94`: `credit_synthesis`, `legal_covenants`, `relative_value`, `committee_challenge`) without a `module_context`. Under the owner flow a step with `inputs != "none"` gets its body as the step's `read_inputs` view (`_VIEWS`, `owner_workflow.py:~214`; CP-5's is `owners/cp5.py:105-134`), which the workflow journals as an `OwnerInputRead` and requires before submit (`StepSpec` doc; `read_inputs` :1187-1206); embedding such a body would be an orchestrator-side read the model never made. A `MODULE_CONTEXTS` step with `inputs == "none"` (CP-3) has no view, so the composer embeds its `module_context` (H2 below). So:

**CP-5 scope feed (settled here).** The model gets CP-5's scope through the `read_inputs` tool, not in the prompt. The prompt says the `read_inputs` result is the `integrity-scope` CONTEXT block (`SCOPE_BLOCKS[...]`, :857-860, `("integrity-scope", "review scope")`), that it must call `read_inputs` first, judge only the claims listed there, and that the body is not a source and is never cited (the unchanged `CP5_SCOPE_RULE`, :~815, already says this). The same holds for every step with `inputs != "none"` (`module_context`, `step_context`, `projection`). The recorded evidence of consumption is therefore the journaled read, which is what "actual tool use, consumption" needs. Alternative in Q1.

**Composer shape.**

```python
@dataclass(frozen=True)
class PromptRequest:
    step_id: str; spec: StepSpec; pack: PreparedPack
    context: RunContext | None        # context_facts(pack), None without a context source
    store: Execution; attempt: Attempt  # for module_context and settled CP-1 facts (H2)
    submit_tool: str; tool_set: ToolSet; readable: tuple[str, ...] | None
    repair_issues: tuple[str, ...] = ()
    untrusted: tuple[EvidenceItem, ...] = ()   # O7b's retrieved items; empty before O7b
PromptFor = Callable[[PromptRequest], tuple[Message, ...]]   # Message: O5's turn.Message
```

## Task 3: Rule lists and the oracle [mx-precise]

**Files:** `prompts/rules.py`, `prompts/rule_lists/<step>.json` (26 files), `tests/prompts/test_rules.py`.

**What a rule is.** `{"id": "<step>.<n>", "statement": str, "checks": ["<module>:<function>", ...]}`: `id` is stable, `statement` is the sentence the prompt must carry, `checks` are the validator functions (qualified `module:function`) that enforce it.

**Mechanical extraction.** Validator issues are free-form strings without ids (e.g. `cp2a.py:612-674`, `cpl10.py:1011-1120`, `cp3d.py:789,1967`), so rule ids cannot be read from the strings. What is mechanical:
- **Existing 12:** rule ids are the lettered rules of `STEP_CONTRACTS[step]` (`^([a-z])\. `, e.g. `source_readiness` a-h, :681-705) -> `<step>.<letter>`, extracted by regex; `statement` is the whole rule including continuation lines up to the next letter (L4: not truncated to its first line); `checks` are written once by the Task 3 agent from the rule's own comment (`prompts.py:~520`: "each rule states one check its validator makes") and verified by AST below. The orchestrator rules O1-O4 and `build` rules 1-6 are listed as `compose.*` rules and checked the same way.
- **New 14 (M3):** AST alone is not enough: cp8's checks are `_Checker._decision`, `_thesis`, `_sizes` appending to `self.found` (`cp8.py:544-990`), and cp2e and cp3d build issues inline. The frozen oracles list every check: `cases/<m>-owner/expected.json` `refusals` (cp2a 31, cp8 69, cp2e 27, cp3d 19, cpl10 19) plus `tool_use_refusals`. So `checks` holds **oracle refusal ids**; `rules.extract_checks(module)` parses the core with `ast`, follows issue sites reachable from `ENTRY_VALIDATOR` as a cross-check, and emits a draft `rule_lists/<step>.json` with one candidate rule per refusal group, `checks` filled, `statement` empty. Where a core already states its rules in prose (`cpl10.SCREEN_RULES` :1184; the `rules` of cp1c's view :1884) the extractor copies that text as the draft `statement` source, flagged `from_code`.
- **M5:** a different agent from every Task 4 writer completes the 14 `statement`s and `checks` in Task 3; `mx-precise` reviews them, and the lists are then **frozen** (golden file of ids, checks, statements) before any writer starts. Writers cannot edit them, so texts and rules are not one agent's self-consistency.

**Test oracle** (the Done-when's second half):
1. `test_every_content_refusal_is_covered`: every step has a check source and the test fails for any step without one (CP-1B has no `cases/cp1b-owner` oracle: its source is O1's `cp1b` entry validator issue codes, the `build_earnings_delta` `ValueError` codes, `earnings_workflow.py:2098-2106`, reused by O1); every content refusal id of the step's oracle or code list is in some rule's `checks`, and so are the AST issue sites reachable from `ENTRY_VALIDATOR` (a new check without a rule fails). A mutation probe inserts an inline issue into a copied core and expects failure.
2. `test_every_check_exists`: each `checks` entry resolves to an oracle refusal id or an AST function (a removed or renamed one fails).
3. `test_prompt_names_every_rule`: for every inventory step, the composed system message contains each rule's id token `[<id>]` and each rule's `statement` verbatim (the existing 12 carry `statement` = the contract line, so this also proves the contract was not edited).
4. `test_rule_ids_unique_and_stable`: ids unique per step; the committed list of ids is a golden file, so removing a rule needs an explicit golden edit that the review sees.
5. Mutation probe: delete one rule's text from a copied `texts/<step>.md` -> test 3 fails (kept as a test, not left to the reviewer).

What this oracle does not prove (stated in Not verified): that a statement is *accurate* to the check, or that a model follows it. The Task 4 review checks the first; the model-testing framework's fault classification measures the second.
